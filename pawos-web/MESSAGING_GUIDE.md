# PawOS product messaging and content standard

## Canonical product description

PawOS is an AI engineering execution platform. It helps developers work through supported engineering tasks by combining project context, task planning, permissioned actions, execution and result reporting.

Use this description consistently across the website, product pages, sales material and documentation. Do not describe PawOS only as a chatbot, generic AI companion, universal computer agent or autonomous replacement for developers.

## Primary message

**Delegate engineering work. Review what gets done.**

Supporting explanation:

PawOS helps developers investigate issues, understand projects, plan code changes and carry out supported engineering tasks. The available workflow depends on whether the developer uses PawOS Web, CLI or Desktop.

## Product experiences and execution boundaries

- **PawOS CLI:** An independently installed terminal agent. It works from the local folder where it is started, including non-Git folders. Describe only capabilities present in the published CLI release. The repository documents npm 1.2.0 as published; a local 1.2.1 candidate must not be presented as the current public npm release until published and verified.
- **PawOS Desktop:** A Windows application for supported local project, development-tool and environment workflows. Source code or a local build does not establish that a packaged release is certified or publicly available. Confirm the current distribution channel and release status before making download claims.
- **PawOS Web:** Browser-based Chat and Code. Code works with connected GitHub repositories. Web does not read local computer files or run local terminal commands.
- **Mobile:** PawOS Web in a mobile browser or a paired view of an active Desktop session. It is not a separate local execution runtime.

## Core workflow language

Use these terms in this order where they fit the actual workflow:

1. **Understand** — inspect the project context available to the selected experience.
2. **Investigate** — examine relevant files, errors, history or connected information where supported.
3. **Plan** — organize the requested outcome into proposed steps.
4. **Review and authorize** — show proposed work and request confirmation where required.
5. **Execute** — perform supported actions within the workspace, runtime and permission boundaries.
6. **Verify and report** — show checks, outputs, changes, failures and what remains unverified.

Do not imply every task runs through every stage automatically. Describe the actual experience and task.

## Audience

Write for:
- Individual software developers.
- Technical founders.
- Engineering leads and CTOs.
- Software development agencies and engineering teams.

Assume the reader is technically capable but unfamiliar with PawOS. Explain the product in plain engineering language before introducing internal terminology.

## Writing standards

- Prefer precise nouns and verbs over slogans.
- Explain the user problem before listing features.
- Use short paragraphs, concrete examples and meaningful headings.
- Explain where work runs and what data or tools the product can access.
- State when an action depends on plan, account, connector, provider, local setup or permissions.
- Distinguish shipped, limited, unverified, candidate and planned capabilities.
- Use real PawOS screenshots and recordings; do not create fictional product UI.
- Avoid repetitive feature cards and decorative AI imagery.
- Do not name individual competing products in public marketing copy. Use category descriptions such as “AI coding assistants” or “AI development agents” when comparison is necessary.

## Claims that must not be made without evidence

- PawOS completes every engineering task autonomously.
- PawOS replaces developers or entire engineering teams.
- PawOS is more capable or more reliable than every other agent.
- Every connector supports every read and write operation.
- A successful tool call means the application or feature is correct.
- Desktop source code proves a signed, certified or generally available installer.
- A local CLI candidate is publicly published.
- Unverified productivity, time-saving, customer, adoption or reliability metrics.

## Website information architecture

- **Overview:** Product definition, developer problem, workflow, three experiences, real evidence and next steps.
- **Product:** Separate pages for Web, CLI, Desktop, engineering workflows and integrations.
- **Developers:** Installation, quickstart, product comparison, technical guides, API/integration references and troubleshooting.
- **Teams:** Verified team capabilities, permissions, billing and contact path.
- **Trust:** Security, privacy, permissions, data handling and limitations.
- **Resources:** Changelog, roadmap, FAQ, support and company information.

## Review checklist for every public page

1. Can a new developer explain what PawOS does after reading the first screen?
2. Is the intended user clear?
3. Does each capability belong to the named product experience?
4. Are release and availability claims verified?
5. Are approvals and permission boundaries accurate?
6. Are screenshots authentic and correctly captioned?
7. Do calls to action lead to the destination their label promises?
8. Does the page avoid unsupported comparisons, metrics and guarantees?
